### HAMi 对实验口径的影响（必须写进报告）

本集群 HAMi 的正确用法（源自成功样本 `hami-share-a`，2026-09-17 实测验证）：

```yaml
spec:
  schedulerName: hami-scheduler    # 必须显式指定，否则被 k3s 内置调度器抢占
  runtimeClassName: nvidia         # HAMi 部署的 RuntimeClass
  containers:
  - resources:
      limits:
        nvidia.com/gpu: 1          # vGPU 数
        nvidia.com/gpucores: 100   # 算力百分比
        nvidia.com/gpumem: 15000   # 显存 MiB
```

三个易错点：

1. **不指定 `schedulerName: hami-scheduler` 会出现 `UnexpectedAdmissionError: no binding pod found`**——Pod 被 k3s 内置调度器调度，HAMi device plugin 查不到绑定记录，且 Deployment 会重建风暴（实测 165 个失败 Pod）
2. **资源配置用扩展资源（`gpucores`/`gpumem`），不是 `hami.io/*` 注解**
3. HAMi 劫持 NVML，Pod 内 vLLM 看到的是虚拟显存：单 vGPU 给满（gpumem 15000、gpucores 100）≈ 独占整卡；TP=2 请求 2 × 15000 MiB，单卡放不下，必然分散到两张物理卡。同一配置下的对照组数据依然可比，报告注明"经 HAMi 层"

## 1. 目录与双机分工

```text
本地 mac（Git 主副本）                       双 T4 服务器
~/project/study/python/m2/                  ~/leon/m2/
├── 实验手册.md                             ├── k8s/        ← manifests 同步上去
├── k8s/              ← 部署 YAML 在本地改  ├── results/    ← 原始结果落地
├── scripts/                                └── logs/
├── benchmark/
├── quality/  notes/  report/
```

原则：

- **YAML 只在本地修改并 Git 提交**，rsync 到服务器后 `kubectl apply`，不在服务器上手改
- 压测在集群内跑（临时 Pod 访问 Service），mac 不做压测客户端
- 服务器结果"只追加"，拉回本地归档

```bash
# 同步 manifests 和脚本到服务器
rsync -av --exclude '.venv' --exclude '__pycache__' \
  ~/project/study/python/m2/ root@服务器IP:~/leon/m2/

# 拉回结果
rsync -av root@服务器IP:~/leon/m2/results/ \
  ~/project/study/python/m2/benchmark/results/raw/
```

## 2. 固定镜像版本（一次性，最关键）

```bash
# 服务器上直接用 containerd 拉（k3s 会自动拉取，这里先手动确认能拉到并固定 tag）
sudo k3s ctr images pull docker.io/vllm/vllm-openai:<版本tag>

# 记录 tag + digest 到实验记录，Day 1 → Day 18 全程不换
sudo k3s ctr images ls | grep vllm
```

拉取慢：k3s containerd 配置 registry mirror（改 `/etc/rancher/k3s/registries.yaml` 后 `systemctl restart k3s`）——此操作影响全局，若需修改先确认现有 registries.yaml 内容。

## 3. 每次实验的固定流程

```text
① collect_env.sh 采环境快照（含 kubectl 状态）
② 本地改 k8s/*.yaml → rsync → kubectl apply -n llm-lab-m2
③ 等 Pod Ready（kubectl rollout status / logs -f）
④ 验证 HAMi 分配是否符合预期（describe pod + 容器内 nvidia-smi）
⑤ smoke_test.py 冒烟
⑥ 临时 Pod 跑 vllm bench serve → results/ 落地
⑦ kubectl delete 掉本次 Deployment，保存日志
⑧ rsync 拉回本地、Git 提交
```

创建命名空间（一次性）：

```bash
kubectl apply -f k8s/namespace.yaml
```

## 4. 实验 1：冒烟（Qwen2.5-1.5B，单 vGPU）

### 4.1 部署

```bash
kubectl apply -f k8s/vllm-smoke.yaml
kubectl -n llm-lab-m2 rollout status deploy/vllm-smoke --timeout=10m
kubectl -n llm-lab-m2 logs -f deploy/vllm-smoke
```

关注日志中的关键行并记录：

```text
# ...GPU KV cache size: N tokens
# ...Maximum concurrency for 4096 tokens per request: X.XXx
```

### 4.2 验证 HAMi 分配（每个实验都要做）

```bash
# 看 HAMi 实际分配的卡和资源
kubectl -n llm-lab-m2 describe pod -l app=vllm-smoke | grep -A 5 -i nvidia

# 容器内视角：虚拟显存是否 ≈ gpumem 声明值（15000 MiB）
kubectl -n llm-lab-m2 exec deploy/vllm-smoke -- nvidia-smi
```

同时确认 Pod spec 中 `schedulerName: hami-scheduler` 已生效、`hami.io/bind-phase: success` 注解存在——这是 HAMi 调度链路走通的标志。

### 4.3 冒烟测试

```bash
kubectl -n llm-lab-m2 port-forward deploy/vllm-smoke 8000:8000 &
curl -s http://127.0.0.1:8000/health && echo OK
python3 scripts/smoke_test.py --base-url http://127.0.0.1:8000 \
  --model qwen2.5-1.5b --rounds 3
```

记录：模型下载/加载耗时、KV Cache 容量、首次请求 vs 预热后延迟。

### 4.4 清理

```bash
kubectl -n llm-lab-m2 logs deploy/vllm-smoke > ~/leon/m2/logs/smoke-1.5b.log 2>&1
kubectl delete -f k8s/vllm-smoke.yaml
```

## 5. 实验 2：7B FP16 双卡基线（TP=2）

```bash
kubectl apply -f k8s/vllm-7b-fp16-tp2.yaml
kubectl -n llm-lab-m2 rollout status deploy/vllm-7b-fp16-tp2 --timeout=15m
```

验证要点：

- **两个 vGPU 必须落在两张不同物理卡**：`describe pod` 看 HAMi 分配信息；若落在同一卡（理论不应发生，15000×2 放不下一张卡），停下来排查
- 双卡容量按 GPU 1（Free ≈ 14912 MiB）口径估算
- 启动失败或 KV Cache 过小 → 保留日志，降 `max-model-len` 重试，不要直接拉高 util

## 6. 实验 3：压测

压测脚本 `benchmark/run_bench.sh` 在集群内起临时 Pod（不占 GPU），通过 Service DNS 访问服务，结果经 hostPath 直接落 `~/leon/m2/results/bench/`：

```bash
cd ~/leon/m2 && bash benchmark/run_bench.sh \
  --service vllm-7b-fp16-tp2 \
  --label fp16-7b-tp2 \
  --model qwen2.5-7b \
  --exp-id EXP-20260917-1 \
  --input-len 1024 --output-len 128 \
  --num-prompts 300 --concurrency 8
```

脚本行为：

- 校验 Service 存在 → 生成压测 Pod（`activeDeadlineSeconds: 3600` 兜底）
- 实时输出日志，结束后日志存 `~/leon/m2/logs/`，结果 JSON 存 `~/leon/m2/results/bench/`
- 正常结束自动删 Pod；异常时保留 Pod 供排查，按提示手动清理

四类标准工作负载定义见 `benchmark/workloads.yaml`。规范：预热 10 个请求、每组重复 3 次取中位数、p99 需 ≥300 样本、每个结果 metadata 必须带 `--exp-id` 实验编号。

## 9. 排查表

| 现象 | 检查 |
|---|---|
| `UnexpectedAdmissionError: no binding pod found` + Pod 重建风暴 | Pod 缺 `schedulerName: hami-scheduler`，被 k3s 内置调度器调度；先 `scale --replicas=0` 止血再 `delete pod --field-selector=status.phase=Failed` 清理 |
| Pod Pending | `kubectl describe pod` → 看 HAMi scheduler 是否无资源可分；gpumem 是否超过单卡容量 |
| 容器内显存不对 | resources.limits 的 gpumem/gpucores 是否正确；先跑 4.2 验证步骤 |
| 两个 vGPU 同卡 | 不应发生（15000×2 > 单卡）；检查 HAMi 显存分割配置 |
| 镜像拉取失败 | k3s registry mirror；镜像 tag 是否存在 |
| 启动 OOM / KV Cache 为 0 | HAMi 虚拟显存口径下 util 是否过高；降 max-model-len |
| 压测连不上 | Service 名与命名空间拼写；`kubectl -n llm-lab-m2 get svc,ep` |
| TTFT 抖动 | 是否与现有 k3s 负载抢 CPU（当前水位极低，基本无风险）；是否忘记预热 |
